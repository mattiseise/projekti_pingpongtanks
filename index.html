Ping Pong Tanks: what you build and how you proceed

You build Ping Pong Tanks in Unity from your own Game Design Document (GDD), the document that says what the game is and how a round plays out: a tank arena where two players share one keyboard, fire bouncing shells through a generated maze and grab power-ups. On 4 December the client gets version 1.0, the minimum viable product (MVP), which anyone at school can download and start from your written guide.

You decide how each feature is built, write the expected result of every test before you play, and keep all your work in the public repository. The Unity version, the licence, the release channel and your public name are agreed with your instructor, not decided by you or by AI.

How to use the weekly guide

  1. Read how the week connects to the whole project, and the week goal.
  2. Do the week's work steps in order. The first unfinished work step is open. Tick a part as soon as you have done it: a tick is your own memory, not a submission.
  3. When a work step changes the game, do each change as a GitHub issue and work through it with the six steps on the Way of working page. One work step can need several issues.
  4. Do the end-of-week check. Write the three project journal fields, download the whole journal and commit it as project-docs/project-journal.md, replacing the old file.

Work step is one numbered item in this site's weekly guide. GitHub issue is a numbered task card in your repository for one change to the game, usually half a day to a day of work, closed by the commit that finishes it. Working method is the six steps on the Way of working page (pick, plan, build, test, save, record) that you repeat for every issue.

Game parts and tools
Unity project (the agreed version)
Scenes, prefabs and scripts live in Assets/ at the repository root. A prefab is a Unity object saved as a reusable template: the tank, the shell and the power-up pickup. Builds, the packaged runnable versions of the game, do not go into Git.
C# scripts
Movement, shooting, rounds, the maze generator, the power-up system and the menus. You write the game's code yourself. The script names in the implementation help are suggestions.
Unity 2D physics
Rigidbody2D, Collider2D and Physics Material 2D do the movement, the collisions and the ricochets. Moving objects past the physics breaks the ricochet, so it is used from week 37 on.
Data outside the code
The arena configuration and the power-up data are data, not if branches in code. You compare ScriptableObject, a JSON file and PlayerPrefs in week 40 and choose the store for both; JSON is a plain-text data format that people and programs can both read. Player settings go into PlayerPrefs in week 46, as agreed. If the week 40 comparison clearly favours another store for them, agree the change with your instructor before week 46.
Git and GitHub
A public repository: the Unity project, the issues and the milestone "MVP 4 Dec", small commits, pull requests from week 44 on, and the release. .gitignore keeps Library/, Temp/ and builds out of Git.
Build and release
A Windows build or the target agreed with your instructor. Release candidate v1.0-rc1 in week 47, and v1.0 in week 48 as a GitHub Release or on itch.io, as your instructor decides.
Graphics and sound
Simple graphics you draw yourself: a square body, a round turret and tile textures. Sprite packs only with the source and the licence in a CREDITS file. Sound only if the week 43 prioritisation picks it.
AI
May explain error messages, unpack Unity concepts and suggest test cases. The game's code, the game design decisions and the test results are yours. Every significant use goes into the AI log.

Original brief · issued 31 August 2026

Build the game you designed — and prove it works

I have read your Game Design Document for Ping Pong Tanks, and I am commissioning exactly the game it describes: a fast top-down tank arena for two players on one keyboard. My terms are simple. I am not buying a promise, I am buying a working build with its test log. Two players, one keyboard, and the tanks must feel responsive from the first week. I expect the game to be playable at the end of every single week — a little better each time — and the whole project to live in a public GitHub repository I can open whenever I want.

The design lives or dies on its core loop, so follow the GDD's own rules to the letter: one shell per tank, endless ricochets, roughly ten seconds of life, and no point awarded if both tanks die within five seconds of each other. The bouncing shell is the soul of this game — if the ricochet feels wrong, nothing else matters. A round of Ping Pong Tanks should take seconds, not minutes — quick deaths, quick restarts. Randomly generated mazes are what keep the matches fresh — no two rounds should look the same. And chaotic power-ups keep every match fresh — but the player must always see who has what.

I will not wait until December to see the game. Halfway through, I want to see the game and decide with you what actually fits before the deadline — the GDD holds more ideas than thirteen weeks can carry, and cutting together is part of the job. When I give feedback, act on it in a branch and show me the merge: feedback only counts when I can point at the commit that answers it. When you tell me the game is chaotic but fair — that balance is proven with a test log, not with a feeling.

The Minimum Viable Product (MVP) — the smallest version of the game that contains the required playable core — is due on Friday 4 December 2026. Keep the user interface out of the way: low clutter — menus should get the players into the match, not stand in their way. Before you call it released, hand the build to someone outside the project on another machine: if a stranger cannot start the game from your written instructions alone, it is not released — it is just on your machine. Version 1.0 means I can hand the link to anyone at school and it just works. After that, the last week belongs to the handover — in the final week you are not building the game anymore, you are proving what you know.

Who is the client? The client in this brief is your instructor, who commissioned the game. Your instructor receives your question list in week 36 and plays the game as the client in the week 43 review.

Priority levels. P0 is the required core: the features that must be finished, or there is nothing to hand over. P1 is important follow-up content that gets built only once P0 works, and P2 is optional extra that can be left out.

Requirement · P0 for this project: a two-player match, a bouncing shell, rounds and scoring with the 5 s rule, a procedurally generated 10×10 maze that is new every round, three power-ups, a menu path and a released v1.0. Released as a GitHub Release (or on itch.io — the instructor decides).

Requirement · hold the scope

These are NOT built without the week 43 prioritisation decision: homing missile, cluster bomb, laser, triple shot, special tiles (water, smoke, one-way, portal), the Forest and Snow themes, sound and music, merged power-ups and online play. They are in the GDD — they are not in the MVP; they stay on the P1 and P2 lists. Three half-finished features are worse than one finished one.

Working method · one GitHub issue at a time

Six steps, every time

This is the working method for one change to the game. The weekly guide tells you which work steps to do this week. Inside a work step that changes the game, repeat these six steps for every GitHub issue, then go back to the work step and tick its parts.

  1. 1Pickone GitHub issue from the top of the backlog
  2. 2Planread the GDD section and the GitHub issue
  3. 3Buildone piece at a time
  4. 4Testplay it and record the result
  5. 5Savecommit and push
  6. 6Recordwhat you produced and learned

Rule of thumb: if you cannot explain the change, the work is not finished.

Open only the current week. Read how the week connects to the whole project and the week goal, do the work steps in order, then do the end-of-week check and fill in the week's project journal.

Weekly meeting: on Mondays, 15 minutes with the game team. Record what you agree on the GitHub issues it concerns; that is always the primary place. Write a separate project-docs/meetings/weekNN.md only in weeks where a work step asks for one. In the repository, people appear only by role, for example instructor or game team member B.

Test like a developer

Testing is not just playing with a friend. Record the expected result, the observed result, the cause of the bug, the fix and the retest.

  • At least 12 planned test cases with the expected result recorded before the run — the numbered test cases (T01, T02, …) from the feature weeks count (14+ in the plan).
  • 3 complete debugging chains. A debugging chain is one bug written up end to end: observation → reproduction steps → cause → fix commit → retest → regression test.
  • Test classes in roughly equal thirds: normal use, boundaries and error cases — the GDD's own risks first: collision accuracy, spawn fairness, the 5 s rule, despawn timing and power-up frequency.
  • The release is tested in a clean environment, on a machine that has never had the project on it.
